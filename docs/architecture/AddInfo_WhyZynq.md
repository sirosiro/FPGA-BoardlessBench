# なぜ F-BB は Zynq をリファレンスアーキテクチャに選んだのか

FPGA-BoardlessBench (F-BB) は、特定のベンダーや特定のチップに依存しない汎用的なテスト環境でありながら、標準のプロダクション・リファレンスアーキテクチャとして **Xilinx Zynq-7000 / UltraScale+** を掲げています。

本ドキュメントでは、F-BB がなぜ Zynq を標準モデルに選定したのか、その理由と設計スタンス、そして NXP などの他社 SoC や独自仮想 SoC への拡張性について説明します。

---

## 1. 業界のデファクト・スタンダード（共通言語としての認知的アンカー）

組み込み Linux と FPGA を組み合わせたヘテロジニアス SoC の世界において、**Xilinx Zynq シリーズは最も広く認知され、世界中の現場で採用されているデファクト・スタンダード** です。

もし F-BB を「架空の高性能な仮想 FPGA SoC 環境です」と説明してしまうと、現場の組み込み・ファームウェアエンジニアにとって具体性が薄れ、「自分の開発現場でどう役立つのか」が直感的に伝わりにくくなります。

最も知名度が高く親しみのある **「Zynq」を共通言語・認知的アンカー（拠り所）として提示する** ことで、エンジニアは即座に実機の開発現場（Aコア Linux、Mコア RTOS/ベアメタル、PL 側の AXI バスや GPIO/UIO レジスタ）をイメージでき、導入の心理的ハードルを大幅に下げることができます。

---

## 2. 「大は小を兼ねる」網羅的かつリッチなペリフェラル構成

Zynq は、現代の組み込みシステムに求められる主要なハードウェア要素を網羅しています：

* **GPIO (MIO / EMIO)**: 最大 118ch の広大な I/O 空間
* **高速 DMA (AXI CDMA)**: メモリ間転送、アライメント制約、バウンダリ保護
* **シリアル通信バス**: 多重 I2C、SPI（マルチスレーブ Flash & ADC）、UART
* **マルチコア協調 (AMP / RemoteProc)**: Aコア (Linux) と Mコア (ベアメタル/RTOS) の共有メモリ・割り込み通信

このように、**最も複雑で機能がリッチな Zynq を標準ベースとして成立させておくことで、よりシンプル、あるいは異なる構成を持つ他の SoC にも余裕をもって対応できる（大は小を兼ねる）** というアーキテクチャ上の合理性があります。

---

## 3. F-BB の本質：Zynq に特化しない「SoC / ベンダー非依存」の汎用性

F-BB の本質は「Zynq の内部回路を模倣するハードウェア・クローン」ではなく、**DTS（Device Tree Source）駆動のオープンかつ汎用的な仮想 FPGA SoC プラットフォーム** です。

アドレス空間、レジスタ配置、ペリフェラル構成はすべて `config.dts` で宣言的に定義されているため、Zynq 以外の SoC にも柔軟に対応できます。

### 他社 SoC への展開（例: NXP i.MX シリーズ）
F-BB では、NXP の **i.MX 8M Plus** や **i.MX 95** などを想定したシナリオ（例: [P01_frdmIMX: i.MX95 / i.MX 8M Plus HAL シナリオ](../../tests/scenarios/P01_frdmIMX/)）も標準で実装されています。
DTS の互換ノード（`compatible`）やアドレスマップを適切に定義し、HAL（Hardware Abstraction Layer）を構成することで、**NXP やルネサス、TI、Microchip 等の多様な組み込み SoC のファームウェア検証にも工夫次第で自在に対応可能** です。

---

## 4. Zynq に固執しない「完全オリジナルの仮想 FPGA SoC」の創出

実機の物理ボードでは、「ピン配置の制約で特定のペリフェラルが同時に使えない」「基板のバス幅やアドレスマップの変更に物理的な再配線や再基板設計（数週間〜数ヶ月）が必要」といった物理的な足枷が存在します。

F-BB では、特定の商用チップ（Zynq 等）の仕様に縛られる必要すらありません：

* **理想的な独自アーキテクチャの先行検証**:
  自分たちのプロジェクトにとって最も効率的なカスタムレジスタ、独自 DMA エンジン、拡張 GPIO 構成を持つ **「Zynq を超える仮想オリジナル SoC」** を DTS と Verilog で自由に定義できます。
* **シフトレフト（先行開発）の極大化**:
  物理基板の完成を待つことなく、理想のインターフェース仕様に基づいたロジックの蒸留とファームウェアの先行結合テストを完結させることができます。
