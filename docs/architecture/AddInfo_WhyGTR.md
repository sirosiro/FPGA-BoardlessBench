# なぜ F-BB は独自DTSをやめて GTR を採用したのか
**〜「NIH症候群」の罠と、SystemRDL等の既存規格に対するアーキテクチャ上の必然性・実用主義トレードオフ〜**

---

## 1. はじめに: 「オレオレ規格」への警戒と、その必然性

「学習コストが高いから」という理由だけで独自規格を作るのは、ソフトウェア工学的には確かに最も警戒されるアンチパターン（いわゆる **NIH症候群：Not Invented Here**）です。まともなエンジニアであれば、「業界標準規格を学ぶコストを嫌ってオレオレ規格を作るなんて本末転倒ではないか？」と疑問を抱くのは当然の技術的良心と言えます。

しかし、FPGA-BoardlessBench (F-BB) がかつての「独自拡張DTS」を廃止し、**GTR (General Tree Registers)** という分離アーキテクチャを採用した実態は、

**「問題のドメイン（目的）に対して、既存の業界標準ツールが根本的にオーバースペックかつミスマッチだった」**

というアーキテクチャ上の必然性に基づいています。

本ドキュメントでは、F-BB がなぜ当初の独自拡張DTSから脱却したのか、なぜ SystemRDL や IP-XACT などの既存規格をそのまま採用しなかったのか、そして GTR がどのように「Linuxカーネルの世界的規約への敬意」と「PC単体でのアジャイルな先行開発速度」を両立させているのか、その設計思想を解説します。

---

## 2. 背景：かつての「独自拡張DTS」が抱えていた2大問題（ADR #015）

初期の F-BB では、`config.dts` のノード内に直接 `registers = ...;` という独自プロパティを記述する「独自拡張DTS方式」を採用していました。1つのファイルから Cヘッダー (`vfpga_device_config.h`) や Verilog スケルトン、WebダッシュボードUIを自動生成できる「単一の情報源 (Single Source of Truth: SSOT)」の利便性を最優先したためです。

しかし、プロジェクトの発展とともに、この方式は以下の **2つの重大な破綻** を引き起こしました。

### (1) 初学者の教育的純度の危機（Linuxカーネル・Linusコミュニティ規約違反）
Linux カーネル標準の Device Tree (`.dts`) は、本質的に **「ハードウェアトポロジー（物理アドレス空間、バス構成、クロック、割り込み線）」** をOSに伝えるための仕様記述言語です。

チップ内部の各レジスタ詳細（オフセット、ビットフィールド、アクセス権限など）を DTS に書き込むことは、Linus Torvalds 氏をはじめとする Linux カーネルおよび Device Tree コミュニティが **「厳格に禁じている重大なアンチパターン」** です。

F-BB で学んだ初学者が「DTS にレジスタ定義を直書きするのが正しい」と誤解したまま実務や Linux OSS コミュニティに参加した場合、コミュニティからの手厳しい叱責を受けたり、誤った知識が定着してしまいます。「ボードレス環境で初学者が本物の組込みLinux開発を学ぶ」という教育的誠実さにおいて、これは絶対に看過できない問題でした。

### (2) 実機透過移行（Sim-to-Real）の破綻
独自プロパティ `registers` が混入した DTS は、標準のデバイスツリーコンパイラ（`dtc`）や実機 Linux（PetaLinux / Yocto / Buildroot 等）のビルドに通りません。

そのため、F-BB で先行開発したファームウェアを実機 FPGA ボードへ移植する際、エンジニアが手作業で独自プロパティを削り取ったり、実機用とシミュレータ用で2重に DTS を二重保守しなければならず、ヒューマンエラーや同期ズレの温床となっていました。

---

## 3. 既存規格（SystemRDL等）と GTR が解こうとしている問題の違い

では、独自拡張をやめるにあたって、すでに半導体業界でデファクトスタンダードとなっている **SystemRDL** や **IP-XACT** をそのまま採用すれば良かったのでしょうか？

ここに「問題ドメインのミスマッチ」が存在します。

### 比較表: 業界標準規格 vs F-BB GTR

| 比較項目 | 業界標準（SystemRDL / IP-XACT） | F-BBの GTR (General Tree Registers) |
| :--- | :--- | :--- |
| **主戦場・主目的** | ASIC/大半導体ベンダーのチップ設計<br>（RTL自動生成、UVMテストベンチ、PDF仕様書の一括生成） | **PC上でのファームウェア先行開発・即時論理デバッグ** |
| **対象レイヤー** | ビットフィールド詳細、クロックドメイン、リセット挙動、ハードウェア副作用、階層化バスブリッジ | **アドレス空間、レジスタ名、オフセット、アクセス権限（RO/WO/RW）** |
| **更新頻度** | 設計上流で厳密に固めてからリリース<br>（ウォーターフォール寄り） | 「今、このレジスタ1個足してFWの `if` 文を試したい」<br>（秒単位のアジャイル開発） |
| **ツールの依存関係** | Python/Java/EDAベンダー製の重厚なジェネレータ、パーサー、ANTLR環境の連携が必要 | **C言語プリプロセッサ（DTS overlay）の規約のみ** で完結（追加バイナリ不要） |
| **環境構築負荷** | 数百MB〜数GBのツールチェーン導入、ビルド設定の習得が必要 | `git clone` して即実行可能（Docker / devcontainer に即収まる軽量さ） |

### 「画鋲を刺すために巨大な油圧ショベルを持ち出さない」
SystemRDL は「半導体チップを1から設計し、数億円をかけてテープアウトするための巨大な Single Source of Truth」です。

それに対して F-BB が求めているのは、**「C-Shim（`libfpgashim.so`）にアドレスを通し、Webダッシュボードの Transaction Logger や GDB 拡張にレジスタ名を表示させるための最小限のメタデータ」** だけです。

「画鋲を壁に刺したいだけなのに、巨大な油圧ショベルを持ち出して現場を塞いでしまう」ような過剰設計を避けるのが GTR の目的です。

---

## 4. 「DTSとの構文一致」が生む真の価値

開発者が学ぶべき対象を増やさないための工夫が、むしろ GTR には周到に組み込まれています。

### (1) メンタルモデルの分断を防ぐ
* **もし SystemRDL を導入した場合**:
  開発者は「Linuxカーネル用の DTS」と「レジスタ用の RDL」という **2つの全く異なる言語・文法・メンタルモデル** を往復し、それらを束ねる複雑なビルドスクリプトを保守しなければなりません。
* **GTR の場合**:
  構文自体は完全に **「Linux の Device Tree Overlay（参照結合構文）」** そのものです。

```dts
/include/ "config.dts"

&my_timer {
    registers = "CR_CTRL @ 0x00 : RW", 
                "SR_STATUS @ 0x04 : RO";
};
```

### (2) 学習コストは実質「1分」
新しい言語仕様や構文規則を一から覚える必要はありません。「DTS のノード参照構文（`&label`）を使って、属性を1行追加しているだけ」です。

開発者に求められる実質的な学習コストは、**「`registers = "名前 @ オフセット : 権限"` という文字列表記ルールを1分眺める」** だけで済みます。

## 5. F-BB の設計思想：「DTS標準へのリスペクト」と「実用主義」の落としどころ

もし F-BB が「何でもかんでも DTS の中に独自プロパティとしてねじ込む」アプローチに固執していたら、それは悪しきオレオレ仕様です。本番 DTS を汚染し、実機に持っていけないからです。

逆に「完璧なエコシステムを目指して SystemRDL コンパイラを必須にする」と、Docker イメージは数倍に肥大化し、ちょっと Lチカや I2C センサの制御ロジックを検証したいだけの開発者が環境構築の段階で力尽きてしまいます。

F-BB が到達した落としどころは、以下の 3点に集約されます：

1. **本番の `config.dts` は1文字も汚さず 100% Linux 標準準拠にする**
   （実機 PetaLinux / Yocto / Vivado へ無改造でそのまま投入可能）
2. **エミュレータ・シミュレータに必要な仮想契約だけを `config.gtr` に逃がす**
   （二層分離による責任境界の明確化）
3. **その `config.gtr` も、DTS と同じ文法（Overlay & Include）で記述できる**
   （初学者の認知負荷ゼロ、余分なツール依存ゼロ）

この構成は、単なる手抜きではなく **「Linuxカーネルの標準規約を最大限尊重しながら、PC単体でのプロトタイピング速度を最速にする」** ための極めて意図的なエンジニアリング・トレードオフです。

---

## 6. 将来の拡張性（Sim-to-Real と EDA エコシステムとの共存）

GTR の採用は、SystemRDL や IP-XACT、ARM CMSIS-SVD などの既存規格を否定・排斥するものではありません。

むしろ、既存の大規模な設計資産を活かしながら PC での超高速プロトタイピングを実現するため、**「既存の業界標準規格から `config.dts` および `config.gtr` を自動生成する軽量な変換スクリプト（トランスパイラ）」** を連携させるアーキテクチャを想定・計画しています。

### (1) ARM CMSIS-SVD からの自動生成 (`svd2gtr`)
マイコン（STM32、RP2040、ESP32等）や Cortex-M/A 搭載ヘテロジニアス SoC のレジスタ記述として業界デファクトとなっている ARM CMSIS-SVD (`.svd` / XML形式) は、GTR の二層構造と 1:1 に直結します：

* **SVD の `<peripheral>` 情報** ➔ **`config.dts` の標準ノード**
  * `baseAddress`, `addressBlock`, `interrupt` を抽出し、標準の `reg = <base size>;` および `interrupts = <...>;` を持つ Upstream 準拠 DTS を生成。
* **SVD の `<register>` 情報** ➔ **`config.gtr` の仮想レジスタ契約**
  * `<name>`（レジスタ名）、`<addressOffset>`（オフセット）、`<access>`（`read-only` ➔ `RO`, `read-write` ➔ `RW`, `write-only` ➔ `WO`）を抽出し、`registers = "NAME @ 0x00 : RW", ...;` を持つ GTR ノードを生成。

```bash
# 既存の SVD ファイルから本番 DTS と仮想 GTR を一括生成（構想）
fbb import --svd stm32f4_rcc.svd -o tests/scenarios/my_mcu/
```
これにより、マイコンや SoC ベンダーが公式配布している膨大な SVD 定義ファイルを、手入力の手間なく瞬時に F-BB の先行開発環境へインポートすることが可能になります。

### (2) SystemRDL / IP-XACT からの自動生成 (`rdl2gtr`)
ASIC や大規模 FPGA の設計現場において、ハードウェア設計チームが SystemRDL や IP-XACT をレジスタ設計のマスター（SSOT）として運用している場合でも、GTR との連携は極めてシンプルです。

* 上流の CI/CD パイプラインまたは開発用ホスト側で `rdl2gtr`（`systemrdl-compiler` ベースのエクスポートプラグイン）を実行。
* 生成された `config.dts` と `config.gtr` をリポジトリにコミット、あるいは自動展開。
* ファームウェア開発者は、重厚な EDA ツールチェーンを手元に一切導入することなく、軽量な F-BB 上で数秒でシミュレーションを起動。

### (3) 「上流の重厚さ」と「下流の軽快さ」を両立するラストワンマイル
もし F-BB が SystemRDL のコンパイラや IP-XACT パーサーをランタイムコンテナ内に必須依存として組み込んでしまうと、Docker イメージは数倍に肥大化し、「`git clone` してすぐに動く」という F-BB の最大の美点が損なわれます。

変換スクリプトを **「上流（EDA/Chip設計）から下流（FW先行開発）への片道アダプタ」** として位置づけることで：
1. **EDA 資産との完全な相互運用性（資産の再利用）**
2. **F-BB 実行環境のゼロ依存・秒速起動（アジャイルな先行開発）**

という、相反する要求を両立させることができます。

GTR は、重厚な EDA 業界標準規格と競合・対立するものではなく、**「プロトタイピングの現場と巨大な規格との間を埋める、最も軽快なラストワンマイルのインターフェース」** として設計されています。
